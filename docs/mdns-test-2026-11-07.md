# mDNS test, 2026-11-07

Device: ESP32-S3, MAC `14:c1:9f:5c:c8:b4`, IP `192.168.31.211`.
User-reported router: Xiaomi AX3000E, MiWiFi Stable 1.0.30.
PC adapter: Ethernet, `192.168.31.56/24`; the user reported that the lance was
on normal WiFi, so this tests the LAN-to-WiFi path.

## Checks performed

- Before: API reported `3.1.2-esp32s3`, boot ID `2804173788`. No response to new mDNS names; Windows resolution failed.
- `pio run -e esp32s3` passed: flash 827505 bytes, RAM 105708 bytes.
- OTA through `upload_firmware.ps1 -DeviceUrl http://192.168.31.211`: verified firmware, automatic restart.
- After: `3.1.3-esp32s3`, boot ID `3629679998`.
- Repeated UDP DNS queries to `224.0.0.251:5353` over Ethernet, receiving on port 5353 with multicast membership. Responses received from `192.168.31.211:5353`.
- A: `<legacy-host>.local` -> `192.168.31.211`.
- PTR: `_<legacy-service>._tcp.local` -> `<legacy-instance>._<legacy-service>._tcp.local`.
- SRV: target `<legacy-host>.local`, port 80.
- TXT: `id=14c19f5cc8b4`, `path=/api/current`, `firmware=3.1.3-esp32s3`.
- Windows `socket.gethostbyname`: `192.168.31.211`.
- HTTP `http://<legacy-host>.local/api/current`: status 200, `sensor_ready=true`, `storage_ready=true`, `scd_errors=0`, all sensor validity flags true at sequence 4.

Result: mDNS and DNS-SD work between this PC and the lance on the existing
network without router changes. No actual DHCP address change or WiFi
disconnection was triggered, so rediscovery after those events remains untested on hardware.

## Naming change, 2026-11-09

The original host and service names above are represented by placeholders.
This historical test predates the English naming convention. Current source
uses `fnc-fogger-<MAC suffix>.local` and `_fnc-fogger._tcp.local`. The historical
result does not constitute a hardware test of the renamed service. Update
firmware and viewer together; this change does not upload firmware.
